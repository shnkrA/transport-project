# Транспортне підприємство «Транзит»

Навчальний вебзастосунок для оформлення пасажирських і вантажних замовлень та базової роботи з автопарком. Система моделює взаємодію клієнта, диспетчера, водія й механіка. Це прототип: частина даних про маршрути та розклад є локальною, а замовлення не є квитками чи підтвердженим договором перевезення.

Навчальний проєкт з дисципліни «Аналіз вимог до програмного забезпечення», Національний транспортний університет, варіант 9. Автор: Шинкарь А. П., група ІПЗ-24121.

## Ролі користувачів

| Роль | Реалізовані можливості |
| --- | --- |
| Клієнт | Реєстрація та вхід; перегляд доступного транспорту й маршрутів; оформлення пасажирського або вантажного замовлення; перегляд власних рейсів. |
| Диспетчер | Перегляд замовлень, що очікують підтвердження, та підтверджених рейсів; призначення водія для не залізничного рейсу; підтвердження або скасування рейсу; перегляд автопарку й зміна стану транспортного засобу. |
| Водій | Перегляд призначених автобусних і вантажних рейсів; завантаження дорожнього листа у PDF; початок і завершення рейсу; повідомлення про затримку або поломку. |
| Механік | Перегляд транспорту з відкритими повідомленнями; зміна стану транспортного засобу; закриття повідомлення про ремонт із записом опису робіт і вартості. |
| Адміністратор | Доступ до загальної оглядової сторінки та списків рейсів і транспорту. Окремої адміністративної панелі й керування обліковими записами через інтерфейс немає. |

Клієнтський інтерфейс спрямовує користувачів до сторінок відповідно до ролі. Окремі операції диспетчера, водія й механіка на сервері також перевіряють сесію та роль.

## Функціональні можливості

### Пасажирські перевезення

- Маршрути підбираються за точним напрямком із локального каталогу `route_catalog`.
- Для доступної пропозиції відображаються тип транспорту, маршрут, дата й орієнтовна ціна.
- Для поїзда клієнт обирає тип місця та номери місць; кількість вибраних місць має відповідати кількості пасажирів.
- Клієнт надсилає замовлення зі статусом очікування підтвердження. Диспетчер перевіряє та підтверджує рейс.
- У клієнтському кабінеті доступні власні майбутні та минулі рейси.

Орієнтовна ціна розраховується за відстанню й кількістю пасажирів. Для автобуса використовується базова ставка 1,6 грн за кілометр на пасажира з коефіцієнтом 1,5. Для поїзда коефіцієнти типу місця: сидяче — 1, плацкарт — 1,25, купе — 1,8.

### Вантажні перевезення

- Клієнт указує маршрут, дату, вагу, габарити й опис вантажу та обирає доступну вантажівку.
- Інтерфейс перевіряє, чи не перевищує введена вага вантажопідйомність вибраної вантажівки.
- Замовлення надсилається диспетчеру зі статусом очікування підтвердження.
- Попередня оцінка вартості становить 1,20 грн за кілограм: `вага × 1,2`.

### Диспетчеризація й автопарк

- Диспетчер переглядає чергу замовлень, список підтверджених рейсів і рейси в дорозі.
- Для автомобільного рейсу потрібно вибрати активного користувача з роллю водія. Залізничному рейсу водій не призначається.
- Сервер перевіряє дозволені переходи статусів, доступність транспорту та конфлікти призначення водія й транспорту.
- Стан транспортного засобу можна змінювати на «Доступний», «На ТО» або «Не експлуатується», якщо за ним не закріплений активний рейс.

### Водій і механік

- Водій може почати підтверджений рейс і завершити рейс, який уже в дорозі.
- Для призначеного рейсу водій може сформувати дорожній лист у PDF.
- Під час рейсу водій може надіслати повідомлення про затримку або поломку. Повідомлення про поломку переводить транспорт у стан технічного обслуговування.
- Механік переглядає відкриті повідомлення, записує виконані роботи й вартість, після чого закриває повідомлення. Транспорт повертається до доступного стану, якщо немає інших відкритих повідомлень або активного рейсу.

### Автентифікація та сесії

- Клієнт може створити обліковий запис або увійти за електронною поштою й паролем.
- Паролі зберігаються у вигляді bcrypt-хешів.
- Сесія зберігається на сервері; у браузері використовується cookie `transport_session` з атрибутами `HttpOnly` і `SameSite=Lax`. Строк дії сесії — сім днів.

## Технології та архітектура

| Частина | Технології | Використання |
| --- | --- | --- |

| Розробка та збірка frontend | Vite 5 | Локальний сервер розробки та збірка клієнтського застосунку. |

| Серверний застосунок | Node.js, NestJS 10, Express adapter | REST API, контролери, перевірки доступу та бізнес-логіка. |
| База даних | PostgreSQL 16 | Користувачі, ролі, транспорт, каталог маршрутів, рейси й повідомлення водіїв. |
| Доступ до бази | TypeORM і SQL-запити | Робота з сутностями та виконання запитів і міграцій. |
| Перевірка паролів | bcrypt | Хешування пароля й перевірка під час входу. |
| Перевірка вхідних даних | class-validator, NestJS ValidationPipe | Перевірка DTO та параметрів API там, де вони визначені. |
| Вебсервер frontend | Nginx | Видача production-збірки та проксіювання `/api` до backend. |
| Середовище запуску | Docker Compose | Спільний запуск PostgreSQL, backend і frontend. |

У Docker Compose frontend доступний на `http://localhost:5173`, backend API — на порту `3000`, PostgreSQL — на порту `5433` хоста. Усередині мережі Docker PostgreSQL використовує порт `5432`.

## Підготовка середовища для викладача

Для найпростішого запуску потрібні:

- комп’ютер із Windows, macOS або Linux;
- Docker Desktop із Docker Compose v2 (у Linux можна встановити Docker Engine і плагін Compose);
- сучасний браузер, наприклад Chrome, Edge або Firefox;
- доступ до інтернету під час першої збірки, щоб Docker міг завантажити базові образи та встановити залежності;
- вільні порти `5173`, `3000` і `5433`.

Для запуску через Docker **окремо встановлювати Node.js, npm або PostgreSQL не потрібно**: вони запускаються в контейнерах. Після встановлення Docker Desktop відкрийте його та дочекайтеся, поки Docker Engine запуститься.

## Запуск через Docker Compose

1. Завантажте `TransportProject_для_здачі.zip` і розпакуйте архів у папку з правом запису.
2. Відкрийте термінал у розпакованій папці `TransportProject` — у ній має бути файл `docker-compose.yml`.
3. Переконайтеся, що Compose доступний:

```bash
docker compose version
```

4. Зберіть образи й запустіть сервіси:

```bash
docker compose up -d --build
```

Під час першого запуску це може тривати довше: Docker збирає frontend і backend та ініціалізує PostgreSQL. Перевірте стан сервісів:

```bash
docker compose ps
```

Якщо сторінка ще не відкривається, перегляньте журнал backend:

```bash
docker compose logs -f backend
```

Щоб завершити перегляд журналу, натисніть `Ctrl+C`; це не зупиняє контейнер. Після запуску відкрийте у браузері `http://localhost:5173` і ввійдіть за одним із демо-облікових записів, наведених вище.

Зупинити контейнери можна командою:

```bash
docker compose down
```

Ця команда зупиняє й видаляє контейнери, але зберігає дані PostgreSQL у Docker-томі. Для нового чистого запуску вміст архіву зазвичай достатньо розпакувати в окрему папку: проєкт створить власний том бази.

SQL-файли з `db/migrations` підключені як init-скрипти PostgreSQL. Вони автоматично виконуються під час першої ініціалізації порожнього сховища даних. Якщо том бази вже існує, нові init-скрипти автоматично повторно не запускаються; міграцію наявної бази потрібно застосувати окремо від імені власника відповідних таблиць. Не видаляйте том із даними, якщо хочете зберегти базу.

## Локальна розробка

Потрібні Node.js і npm. У першому терміналі з кореня проєкту запустіть PostgreSQL:

```bash
docker compose up -d db
```

У корені проєкту встановіть залежності за lock-файлом:

```bash
npm ci
```

Потім відкрийте два окремі термінали в корені проєкту й запустіть серверну та клієнтську частини:

```bash
npm run dev:backend
```

```bash
npm run dev:frontend
```

Frontend для локальної розробки доступний на `http://localhost:5173`. Vite проксіює запити `/api` до backend на `http://localhost:3000`. Backend за замовчуванням підключається до PostgreSQL на `localhost:5433` з параметрами з `docker-compose.yml`; за потреби їх можна задати у `.env` відповідно до `backend/src/app.module.ts`.

## Структура проєкту

```text
backend/                 NestJS API та серверна бізнес-логіка
  src/entities/          Сутності бази даних
  src/modules/           Модулі автентифікації, користувачів, рейсів і транспорту
db/migrations/           SQL-міграції схеми PostgreSQL
frontend/                React-застосунок
  src/pages/             Сторінки клієнта й працівників
  src/services/          API-клієнт, сесія та автооновлення даних
docker-compose.yml       Опис сервісів PostgreSQL, backend і frontend
package.json             Скрипти npm workspaces
package-lock.json        Зафіксовані залежності для відтворюваного встановлення
```

## Обмеження прототипу

- Каталог маршрутів і розклад не синхронізуються наживо із зовнішніми перевізниками. Сторінка інтерфейсу радить звіряти розклад поїздів з Укрзалізницею.
- Вибір місць у застосунку не бронює місця в Укрзалізниці; система не отримує фактичну доступність місць.
- Вартість пасажирських і вантажних перевезень є орієнтовною; онлайн-оплати немає.
- Система не формує квитки, договори, рахунки чи товарно-транспортні накладні.
- GPS-моніторинг, автоматичні сповіщення клієнтів, облік пального та пробігу, склад запчастин і бухгалтерська аналітика не реалізовані.
- Окремої адміністративної панелі для керування обліковими записами немає.
